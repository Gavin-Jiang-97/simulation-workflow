# 仿真工作规范

作者要亲自审核代码和结果。这里的规则都服务于两个目的：让作者能快速看懂、判断结果，并避免微小趋势被随机性或代码错误掩盖。

## 代码可读性与注释

作者会阅读并修改代码，所以代码本身要易读：

- 变量名尽量与论文符号或物理含义对应，同一个量全程只用一个名字。
- 关键参数集中放在脚本开头或配置中，不在代码中间散落未说明的常数。
- 主流程与子功能分开，一眼能看出仿真链路的步骤。

注释的详略按代码的重要程度决定。

**项目主体代码**要写详细注释，方便作者快速理解和手动调试：

- 函数和子函数：说明功能、输入和输出。
- 每个运算功能模块：给出描述和对应公式，并说明与技术文档（若有）的对应关系，比如公式号或章节。
- 关键变量：解释含义，并写明单位和维度，例如 `H: 信道矩阵 [Nr, Nt, Nsc]`、`tau: 路径时延（秒）`。
- 非显然的假设和近似，以及为什么这样处理，尤其是绕过某个已知问题的原因。

**子功能验证、Debug 等重要程度较低的代码**简化注释，说明用途即可。

不逐行复述代码在做什么。修改已有代码时，让注释随代码同步更新。

**码文合一。** 代码与技术文档要一一对应：模型、公式和处理步骤一致，符号能对上变量。修改任何一方时同步更新另一方。发现两者不一致时，先判断哪一方正确，不要悄悄只改一边，并在报告中用红色标出。

## Results 报告

新建报告时使用 `assets/results-template.md`。

**篇幅。** 用完整、清楚的句子，不要为了简短而压缩到难以理解，也不要写入审核用不到的内容，因为过长的报告会加长人工审核时间。一张图通常配一到三句话，说明结论和关键数值。

**结构。** 主报告只写当前的最终状态，依次为：当前结论、代码结构、各实验结果、问题与隐患、现象与规律总结。被替代的旧轮次移到 `RESULTS_*_history.md`。

**代码结构。** 用树状结构图描述清楚主体代码中各函数间的关联关系，并标注每个函数的作用。函数关系变化时同步更新。

**图片。** 在对应结果旁放入仿真图，便于直观查看，使用相对路径。常见的 Markdown 预览不能直接显示 PDF，所以 PDF 格式的图用链接给出。

**公式。** 用 LaTeX 书写：行内公式用 `$...$`，独立公式用 `$$...$$` 或 `\[...\]`。不用纯文本或代码块来写公式。

**醒目标记。** 问题和结论要能在扫读时被看到：

- 发现的问题和隐患：`<span style="color:red">**……**</span>`
- 已解决的问题、调整成功的结果：`<span style="color:blue">**……**</span>`

问题解决后，把原来的红色条目改成蓝色，不并列保留两条。只标记真正需要注意的内容，标得太多就不醒目了。

**末尾总结。** 报告最后一节记录测试和调试中发现的现象、趋势与规律，比如所提方案在什么条件下优于基准，在什么条件下表现不佳。被否定的猜测也记下来，避免重复排查。每轮任务都要维护这一节：加入新发现，修正被推翻的结论，不要把规律分散在各轮章节中。

**聊天回复。** 同样用清楚的完整句子。先给结论，再指向报告的文件和章节，不重复报告全文。

## 图片输出

- 格式不限，但同一张图只保留一种格式。比如输出了 PDF，就不再输出 PNG。为了检查 PDF 而临时渲染的图片用完即删，不算输出。
- 绘图细节见 `references/figure-style.md`，绘图时再读。

## 节约 token

- 读取 Results 时，文字已提供所需信息，就不用视觉能力查看图片。
- 为了让上面这条可行，报告要把图中的关键数值和趋势写成文字。
- 需要趋势和数值时，从数据文件或报告文字中读取。
- 新生成且要交付的图看一次，只检查图例、裁切和字号等版式问题。
- 优先按章节读取报告和日志，不必每次通读全文。

## 建模与方案选择

调用工具箱或内置模型、选择处理方式、比较方案时，先读 `references/modeling-pitfalls.md`。核心有三点：

- **模型要匹配：** 核对算法所基于的模型与工具箱内置模型的约定是否一致，比如导向矢量的参考坐标。
- **没有绝对的对错：** 处理方式要根据当前边界条件和实际可获得的信息来选择，并写明依据。
- **利弊要权衡：** 对一个环节有利的设计可能损害另一个环节，要同时评估理想和非理想条件。

## 调试与对比实验

设计对比实验或排查问题前，先读 `references/debug-methods.md`。核心有三种方法：

- **控制变量法：** 让被比较的对象看到相同的随机变量，避免微小趋势被蒙特卡罗随机性掩盖。
- **拆解法：** 把链路分成多个模块，逐段与真值或理论值比较，定位最早出错的环节。
- **退化法：** 把系统退化到答案已知的简单情形，验证通过后再逐个恢复非理想因素。
